# 01. 개념과 용어

## 리버스 프록시(Reverse Proxy)란?

클라이언트의 요청을 **대신 받아** 뒤편의 실제 서버로 전달하고, 그 응답을 다시 클라이언트에게
돌려주는 중간 서버입니다. 클라이언트는 뒤에 실제 서버가 몇 대 있는지, 어떤 주소인지 모릅니다.

```
[브라우저] ──▶ [리버스 프록시] ──▶ [실제 서버들]
            (하나의 진입점)       (숨겨진 백엔드)
```

- **포워드 프록시**: 클라이언트를 대신해 바깥으로 나간다 (회사 방화벽, VPN 등).
- **리버스 프록시**: 서버를 대신해 요청을 받는다 (이 튜토리얼의 주제).

## 이 튜토리얼이 구현하는 패턴: Gateway Routing

하나의 진입점(게이트웨이)이 **URL 경로**를 보고 여러 백엔드 중 하나로 요청을 분배합니다.
Microsoft 클라우드 디자인 패턴 카탈로그의 [Gateway Routing pattern](https://learn.microsoft.com/azure/architecture/patterns/gateway-routing)과
정확히 일치합니다.

```
portal.example.com/a/...  ──▶  Backend A
portal.example.com/b/...  ──▶  Backend B
portal.example.com/c/...  ──▶  Backend C
```

### 왜 쓰는가

| 이점 | 설명 |
|------|------|
| **단일 도메인/엔드포인트** | 사용자·외부 시스템은 URL 하나만 알면 된다. |
| **백엔드 은닉** | 내부 서버 주소·포트·개수가 노출되지 않는다. |
| **독립 배포** | 각 백엔드를 따로 빌드·배포·재시작·스케일 가능. |
| **점진적 마이그레이션** | 레거시 앱과 신규 앱을 같은 도메인에서 경로별로 공존. |
| **횡단 관심사 집중** | 인증·TLS·로깅·레이트리밋을 게이트웨이 한 곳에서 처리. |

## 라우팅 방식: Path vs Host

| 방식 | 예 | 특징 |
|------|----|----|
| **경로 기반(Path-based)** | `portal.example.com/a` | 도메인 1개. 인증서 1장. **이 튜토리얼이 쓰는 방식.** 앱이 자신의 경로 접두사를 알아야 함(PathBase). |
| **호스트 기반(Host/Subdomain)** | `a.example.com` | 앱마다 서브도메인·인증서. 앱은 루트(`/`)에서 동작해 단순하지만 DNS·인증서 관리 부담. |

경로 기반은 "앱이 `/a` 아래에서 서비스된다"는 사실을 앱과 프록시가 **함께** 인지해야 하므로
약간의 설정이 필요합니다. 그 설정이 바로 이 튜토리얼의 핵심입니다
([04-key-techniques](04-key-techniques.md)).

## 관련 용어 정리

- **API Gateway** — 같은 패턴을 API 백엔드(마이크로서비스)에 적용한 것. 인증/레이트리밋/집계 추가.
- **BFF (Backend for Frontend)** — 특정 프론트엔드 전용 게이트웨이.
- **Micro-frontends** — 독립 배포되는 여러 프론트엔드 앱을 한 사이트처럼 합치는 개념.
  그중 "reverse-proxy / route-based composition" 방식이 이 튜토리얼 구조.
- **Ingress** — Kubernetes에서 클러스터 외부 트래픽을 경로/호스트로 라우팅하는 리소스(=게이트웨이 라우팅).
- **YARP** — *Yet Another Reverse Proxy*. .NET용 리버스 프록시 라이브러리. 이 튜토리얼의 포털 구현체.

## 언제 쓰지 말아야 하나

- 앱이 **하나뿐**이고 앞으로도 그렇다면 게이트웨이는 과한 추가 계층입니다.
- 백엔드가 **이미 같은 앱**이라면 프록시 대신 그냥 라우팅(컨트롤러/페이지)을 쓰세요.
- 단순 정적 사이트 합치기라면 CDN/정적 호스팅의 경로 매핑으로 충분할 수 있습니다.
